# Database

PostgreSQL 16, queried through Drizzle ORM on a `pg` connection pool. The schema is owned by
hand-written SQL migrations; Drizzle only describes it so that queries are typed.

| File                            | Role                                                      |
| ------------------------------- | --------------------------------------------------------- |
| `apps/api/migrations/*.sql`     | The schema. Plain SQL, applied in filename order          |
| `apps/api/src/db/schema.ts`     | Drizzle table definitions that mirror the migrations      |
| `apps/api/src/db/client.ts`     | `pool` (the `pg.Pool`) and `db` (the Drizzle instance)    |
| `apps/api/src/db/migrate.ts`    | The migration runner                                      |
| `apps/api/src/db/seed.ts`       | Demo accounts                                             |
| `apps/api/src/db/encryption.ts` | Encrypted column types. See [Encryption](/api/encryption) |

## Tables

| Table               | Created in                    | Holds                                             |
| ------------------- | ----------------------------- | ------------------------------------------------- |
| `users`             | `0001_users_and_sessions.sql` | Accounts. `phone` and `totp_secret` are encrypted |
| `refresh_tokens`    | `0001_users_and_sessions.sql` | Hashed refresh tokens, grouped into families      |
| `audit_logs`        | `0001_users_and_sessions.sql` | Who did what, with JSON metadata                  |
| `passkeys`          | `0002_passkeys.sql`           | WebAuthn credentials                              |
| `files`             | `0003_files.sql`              | Upload metadata. The bytes are in object storage  |
| `schema_migrations` | The runner                    | Name, checksum and time of each applied migration |

Primary keys are UUIDs generated by PostgreSQL (`gen_random_uuid()`), and timestamps are
`timestamptz`.

## Querying

Import `db` and the tables, and write the query:

```ts
import { count, desc, eq } from 'drizzle-orm';
import { db } from '../../db/client';
import { files } from '../../db/schema';

const [row] = await db.select().from(files).where(eq(files.id, id));
if (!row) throw notFound('File not found', 'file_not_found');

const page = await db
  .select()
  .from(files)
  .orderBy(desc(files.createdAt), desc(files.id))
  .limit(query.pageSize)
  .offset(paginationOffset(query.page, query.pageSize));

const [totals] = await db.select({ total: count() }).from(files);
```

Because of `noUncheckedIndexedAccess`, the first element of a result is `T | undefined`. Handle
the missing case; the compiler will not let you forget.

For several statements that must succeed or fail together, use a transaction:

```ts
await db.transaction(async (tx) => {
  await tx.update(users).set({ isActive: false }).where(eq(users.id, id));
  await tx.delete(refreshTokens).where(eq(refreshTokens.userId, id));
});
```

`client.ts` exports the `Transaction` type for functions that accept a `tx`. For raw SQL, use
Drizzle's `sql` template tag with `db.execute()`, or `pool.query()` directly. Always pass values
as parameters.

## Migrations

Migrations are SQL files you write yourself. There is no generator and no diffing: what is in the
file is exactly what runs.

```bash
npm run db:migrate            # apply everything pending
npm run db:migrate -- status  # ✓ applied, · pending
```

How the runner (`src/db/migrate.ts`) behaves:

- It applies `migrations/*.sql` in filename order: `0001_…`, `0002_…`.
- Each file runs in its own transaction, together with the row that records it. A failing
  migration leaves nothing behind.
- It takes a PostgreSQL advisory lock first, so two deploys starting at once cannot both migrate.
- It records a SHA-256 checksum of every file it applies in `schema_migrations`.

### Checksums: never edit an applied migration

On every run, the runner compares each applied file with its recorded checksum. If one differs,
it stops:

```text
Migration 0002_passkeys.sql was changed after it was applied. Restore the original file and put
the change in a new migration.
```

This is deliberate. An edited migration means your database and a fresh one no longer match, and
nothing would tell you. Even a whitespace or comment change counts. Restore the file with
`git checkout` and write a new migration instead.

In local development, when the migration has never left your machine, you can also drop the
database and start again:

```bash
docker compose down -v && npm run docker:up
npm run db:migrate && npm run db:seed
```

### Add a migration

1. Create the next numbered file, for example `apps/api/migrations/0004_notes.sql`:

   ```sql
   -- 0004: notes.

   CREATE TABLE notes (
     id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
     title      text NOT NULL,
     created_by uuid NOT NULL REFERENCES users (id) ON DELETE CASCADE,
     created_at timestamptz NOT NULL DEFAULT now()
   );

   CREATE INDEX notes_created_by_idx ON notes (created_by);
   ```

2. Mirror it in `apps/api/src/db/schema.ts`:

   ```ts
   export const notes = pgTable(
     'notes',
     {
       id: uuid('id').primaryKey().defaultRandom(),
       title: text('title').notNull(),
       createdBy: uuid('created_by')
         .notNull()
         .references(() => users.id, { onDelete: 'cascade' }),
       createdAt: timestamptz('created_at').notNull().defaultNow(),
     },
     (table) => [index('notes_created_by_idx').on(table.createdBy)],
   );
   ```

   `timestamptz` is a small helper at the top of `schema.ts`.

3. Run `npm run db:migrate`.

4. Add the table to the `TRUNCATE` list in `apps/api/tests/integration/setup.ts`, so integration
   tests start with it empty.

Things to keep in mind:

- **The two definitions are not checked against each other.** If the SQL and the Drizzle table
  disagree, queries fail at runtime. Integration tests catch this quickly.
- **Do not write `BEGIN` or `COMMIT`** in a migration; the runner wraps the file already. That
  also means statements that cannot run in a transaction, such as
  `CREATE INDEX CONCURRENTLY`, do not work here.
- **Write migrations that old code survives.** During a deploy the migration runs before the new
  code starts, so add columns as nullable or with a default, and drop columns one release after
  the code stops using them.
- There are no down migrations. To undo a change, write a new migration that reverses it.

### In production

The API image contains the bundled runner and the SQL files. Run it as a one-off step before the
new version takes traffic:

```bash
node dist/migrate.js
```

Docker Compose does this with the `migrate` service and the Cloud Run workflow with a job. The
runner looks for the files in `./migrations` relative to the working directory; set
`MIGRATIONS_DIR` to point elsewhere.

## Connection settings

| Variable            | Default | Notes                                              |
| ------------------- | ------- | -------------------------------------------------- |
| `DATABASE_URL`      | —       | Required                                           |
| `DATABASE_POOL_MAX` | `10`    | Per process. The API in cluster mode multiplies it |
| `DATABASE_SSL`      | `false` | `true` verifies the server certificate             |

Connections open on demand, so importing `db` has no side effects. Size the pool so that
`instances × DATABASE_POOL_MAX`, plus the worker, stays under the server's `max_connections`.

## Looking inside

pgAdmin runs at http://localhost:5050 (`admin@bossbyte.dev` / `bossbyte`). Or use `psql`:

```bash
docker compose exec postgres psql -U bossbyte -d bossbyte -c 'SELECT email, role, phone FROM users'
```

The `phone` column shows ciphertext beginning `v1.` — that is [encryption](/api/encryption) at
work.
