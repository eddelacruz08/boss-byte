# Dashboard overview

The dashboard is `apps/core` (`@bossbyte/core`): a single-page React app that talks to the API
and nothing else. It has no server of its own. In development Vite serves it, and in production
it is a folder of static files behind Nginx or PM2's static server.

## The stack

| Library                                | What it does here                                                                 |
| -------------------------------------- | --------------------------------------------------------------------------------- |
| React 19, Vite 8                       | The app and its dev server and build                                              |
| TanStack Router                        | File-based, type-safe routes. See [Routing](/frontend/routing)                    |
| TanStack Query                         | Server data, caching and mutations. See [API client](/frontend/api-client)        |
| react-hook-form, `@hookform/resolvers` | Forms validated by the shared Zod schemas. See [Forms](/frontend/forms)           |
| Tailwind CSS 4                         | Styling, through the `@tailwindcss/vite` plugin                                   |
| `@bossbyte/ui`                         | Buttons, fields, tables, dialogs, toasts. See [@bossbyte/ui](/packages/ui)        |
| `@bossbyte/shared`                     | Schemas, types, permissions, formatters. See [@bossbyte/shared](/packages/shared) |
| Chart.js, react-chartjs-2              | Charts. See [Charts and maps](/frontend/charts-and-maps)                          |
| Leaflet, react-leaflet                 | The map page                                                                      |
| jsPDF, exceljs                         | PDF and Excel files built in the browser. See [Exports](/frontend/exports)        |
| DOMPurify                              | Cleans user-written HTML before it is rendered                                    |
| react-markdown                         | Renders Markdown, as on the reports page                                          |
| Firebase, `@simplewebauthn/browser`    | Google sign-in and passkeys. See [Sessions](/frontend/auth)                       |

## Run it

From the repository root, with the API running on port 4000:

```bash
npm run dev -w @bossbyte/core        # http://localhost:5173
npm run test -w @bossbyte/core       # Vitest, no backend needed
npm run typecheck -w @bossbyte/core
npm run lint -w @bossbyte/core
npm run build -w @bossbyte/core      # production build in apps/core/dist
npm run preview -w @bossbyte/core    # serves the build on port 5173
```

`npm run dev` at the root starts the API, the worker and the dashboard together. Sign in with a
seeded account, for example `admin@bossbyte.local` and `BossByte-Dev-2026`.

The dev server uses port 5173 with `strictPort`, so it fails instead of moving to another port
when 5173 is taken. The API only accepts browser requests from `APP_URL`, which is
`http://localhost:5173` by default, so a dashboard on another port would be refused anyway.

## How it reaches the API

The browser calls `/api/v1/...` on the dashboard's own origin. Something in front forwards
`/api` to the API:

| Where             | What forwards `/api`                                                       |
| ----------------- | -------------------------------------------------------------------------- |
| `npm run dev`     | Vite's proxy, to `VITE_API_PROXY_TARGET` (default `http://localhost:4000`) |
| `npm run preview` | The same proxy                                                             |
| Docker image      | Nginx, to `API_UPSTREAM`. See [Docker](/deployment/docker)                 |
| PM2               | Your reverse proxy. See [PM2](/deployment/pm2)                             |

Same origin means no CORS, and the refresh cookie is a first-party cookie. Keep it that way
unless you have a reason not to.

The settings are in `apps/core/.env`, which `npm run setup` creates from `.env.example`. Every
value is optional in development. See
[Environment variables](/guide/environment#dashboard-apps-core-env).

Only `VITE_*` variables reach the code, and they are fixed at build time. Declare a new one in
`src/vite-env.d.ts` so `import.meta.env.VITE_YOUR_SETTING` is typed.

## Layout

```text
apps/core/
├── index.html                The single HTML page
├── vite.config.ts            Plugins, the /api proxy, the Vitest setup
├── vitest.setup.ts           jest-dom and axe matchers, jsdom stubs
└── src/
    ├── main.tsx              Configures Zod, then loads bootstrap.tsx
    ├── bootstrap.tsx         Mounts the query client and the router
    ├── router.tsx            createRouter() and its defaults
    ├── routeTree.gen.ts      Generated by the router plugin. Do not edit
    ├── styles.css            Tailwind and the UI package's stylesheet
    ├── routes/               One file per page
    ├── features/             API calls, query options and forms, grouped by feature
    ├── components/           App-level pieces: shell, page header, charts, error states
    ├── lib/                  Helpers that know nothing about any one page
    ├── data/                 The sample properties behind the map and valuation pages
    └── test/                 Test helpers: fetch mock, axe, fixtures, render with Query
```

`@/` is an alias for `src/`, set in both `vite.config.ts` and `tsconfig.json`:

```ts
import { api } from '@/lib/api';
```

The split between the three main folders is by how much a file knows:

- **`routes/`** files are pages. They read the URL, call hooks and lay out components.
- **`features/<name>/`** holds what belongs to one area of the product: its API calls, its query
  options and mutation hooks, and components only that area uses.
- **`lib/`** and **`components/`** are shared by every feature and name none of them.

## What happens at start-up

`src/main.tsx` is two lines:

```ts
import '@/lib/zod-config';

void import('./bootstrap');
```

The first turns off Zod's compiled fast path, which the Content-Security-Policy would block. It
has to run before any schema is defined, so the rest of the app is loaded with a dynamic
`import()` instead of a plain import. See
[Forms](/frontend/forms#zod-and-the-content-security-policy).

`src/bootstrap.tsx` then does the rest:

1. Subscribes to the auth store and empties the TanStack Query cache whenever the session ends,
   so the next person to sign in on that browser never sees the previous person's data.
2. Wraps the app in `QueryClientProvider`.
3. Renders `RouterProvider`. From here the router decides what is on screen.

The root route (`src/routes/__root.tsx`) adds the `ToastProvider` around every page. In
development it also loads the TanStack Query and Router devtools, as floating buttons in the
bottom corners. The condition is `import.meta.env.DEV`, a build-time constant, so a production
build does not contain them.

## Building blocks for a page

These live in `src/components/` and are what the example pages are made of.

| Component                   | Props                                               | Use it for                                                          |
| --------------------------- | --------------------------------------------------- | ------------------------------------------------------------------- |
| `AppShell`                  | `user`, `onSignOut`, `children`                     | The frame around signed-in pages. Rendered once, by the route guard |
| `PageHeader`                | `title`, `description?`, `actions?`                 | The `<h1>`, the browser tab title and page-level buttons            |
| `RequirePermission`         | `permission`, `children`, `fallback?`, `pageTitle?` | Showing something only to roles that may use it                     |
| `QueryError`                | `error`, `onRetry?`, `title?`                       | The error state of a failed query                                   |
| `StatCard`                  | `label`, `value`, `hint?`, `loading?`               | One headline figure. Group several in a `<dl>`                      |
| `AuthLayout`                | `title`, `description`, `children`, `footer?`       | The centred card on the sign-in and registration pages              |
| `FileInput`                 | Native `<input>` props except `type`                | A styled file input. Pair it with `FormField` from the UI package   |
| `BarChart`, `DoughnutChart` | See [Charts and maps](/frontend/charts-and-maps)    | Charts with a text alternative                                      |
| `ErrorFallback`             | —                                                   | The router's error boundary. Set once in `router.tsx`               |
| `NotFound`                  | —                                                   | The 404 page. Set once in `router.tsx`                              |

A typical page puts them together like this. `notes` is the example resource from
[Add a module end to end](/guide/conventions#add-a-module-end-to-end); it is not in the
repository.

```tsx
function NotesPage() {
  const notes = useQuery(notesQueryOptions(1, 20));

  return (
    <RequirePermission permission="notes:read" pageTitle="Notes">
      <PageHeader title="Notes" description="Short notes anyone on the team can read." />
      {notes.isError ? (
        <QueryError error={notes.error} onRetry={() => void notes.refetch()} />
      ) : (
        <DataTable
          caption="Notes"
          columns={columns}
          rows={notes.data?.data ?? []}
          rowKey={(note) => note.id}
          loading={notes.isPending}
        />
      )}
    </RequirePermission>
  );
}
```

`PageHeader` renders a `<title>` element. React 19 moves it into `<head>`, so each page sets its
own tab title (`Notes · BossByte`) without a helper library.

## Styling

`src/styles.css` is the whole stylesheet:

```css
@import 'tailwindcss';
@import '@bossbyte/ui/styles.css';
```

The second import brings in the design tokens (the `brand` colours, for instance) and tells
Tailwind to scan the UI package for class names. See
[Setup in an app](/packages/ui#setup-in-an-app). Pages style themselves with Tailwind classes;
there are no CSS modules and no component stylesheet to maintain.

## What ends up in the bundle

The router plugin runs with `autoCodeSplitting`, so each route's component is its own chunk and
a page is downloaded when it is first opened or hovered. On top of that, the heaviest libraries
are imported only at the moment they are used:

| Library  | Loaded when                                              |
| -------- | -------------------------------------------------------- |
| jsPDF    | An **Export PDF** button is pressed (`lib/exports.ts`)   |
| exceljs  | An **Export Excel** button is pressed (`lib/exports.ts`) |
| Firebase | **Continue with Google** is pressed (`lib/firebase.ts`)  |
| Devtools | Development only                                         |

Leaflet arrives with the map page, because only that route imports it.

`build.chunkSizeWarningLimit` is raised to 1000 kB in `vite.config.ts`. The largest chunk is
exceljs, at about 930 kB, and it is one of the lazy ones.

## Add a page

1. Create `src/routes/_authenticated/notes.tsx` and export
   `Route = createFileRoute('/_authenticated/notes')({ component: NotesPage })`. The route
   tree regenerates while the dev server runs. See [Routing](/frontend/routing#add-a-page).
2. Put the API calls and `queryOptions` in `src/features/notes/api.ts`, typed with the schemas
   from `@bossbyte/shared`. See [API client and data](/frontend/api-client).
3. Add the page to `NAV_ITEMS` in `src/components/AppShell.tsx`, with the permission it needs, so
   the link only shows for roles that can use it.

[Add a module end to end](/guide/conventions#add-a-module-end-to-end) walks through the same
thing together with the API side.

## Tests
